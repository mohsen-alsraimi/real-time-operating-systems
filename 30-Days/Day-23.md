Day 23 — SPI Communication

Today I studied SPI (Serial Peripheral Interface) and learned how the STM32F103 can communicate with external devices such as sensors, displays, Flash memories, ADC/DAC chips, and SD cards using high-speed synchronous serial communication.

I learned the four main SPI signals: SCK, MOSI, MISO, and CS/NSS. SCK is the clock generated by the controller, MOSI carries data from the STM32 to the external device, MISO carries data from the external device back to the STM32, and CS/NSS selects which external device should participate in the communication.

I learned that SPI supports full-duplex communication, meaning transmission and reception can occur simultaneously because MOSI and MISO are separate lines. During every clock cycle, the STM32 can shift one bit out through MOSI while receiving another bit through MISO. I studied the role of the internal shift register, which converts bytes from the CPU into serial bits and reconstructs received serial bits into bytes.

I learned that SPI does not normally contain built-in device addressing like I²C. Instead, devices are selected using their Chip Select (CS) signals. Several SPI devices can share SCK, MOSI, and MISO while having separate CS lines. I also learned that SPI does not provide built-in ACK/NACK or START/STOP conditions like I²C, so the exact command and register communication format is defined by each external device.

I studied CPOL (Clock Polarity) and CPHA (Clock Phase). CPOL determines whether SCK is LOW or HIGH while idle, while CPHA determines the timing relationship used for shifting and sampling data. Their combinations produce SPI Modes 0, 1, 2, and 3, and the correct mode must be selected according to the external device's datasheet.

I also studied MSB-first and LSB-first transmission, 8-bit data frames, SPI clock frequency, and the baud-rate prescaler. The STM32 derives the SPI clock from its peripheral clock and divides it using a prescaler. The selected SPI frequency must remain within the limits supported by the connected device.

I configured SPI1 in STM32CubeMX as a full-duplex controller and studied the commonly used SPI1 pins such as PA5 for SCK, PA6 for MISO, and PA7 for MOSI, depending on the selected pin mapping and STM32F103 package. I also learned how a normal GPIO can be configured as a software-controlled CS signal.

I studied the HAL functions HAL_SPI_Transmit(), HAL_SPI_Receive(), and HAL_SPI_TransmitReceive(). I learned that HAL_SPI_TransmitReceive() demonstrates SPI's full-duplex behavior because one byte can be transmitted while another byte is received during the same clock cycles.

I also studied important SPI registers including CR1, CR2, SR, and DR. CR1 contains major configuration settings such as controller mode, CPOL, CPHA, prescaler, and bit order. CR2 contains additional interrupt and DMA controls. DR is the data register used for transmitted and received data, while SR contains status flags such as TXE (Transmit Buffer Empty), RXNE (Receive Buffer Not Empty), and BSY (Busy).

I learned that SPI can operate using polling, interrupts, or DMA. With DMA, a large block of data can move between SRAM and the SPI peripheral with little CPU involvement, which is useful for applications such as sending large amounts of data to a display or receiving continuous sensor data.

Finally, I compared the three communication protocols studied so far. UART uses TX/RX and does not require a shared clock. I²C uses SDA/SCL, supports device addressing, and allows many devices to share two communication lines. SPI uses SCK/MOSI/MISO/CS, requires more wires, but generally provides faster and full-duplex communication.

The main hardware path I learned was: C variable → HAL → SPI data register → SPI shift register → SCK/MOSI physical signals → external device, while received data travels in the opposite direction through MISO → shift register → SPI data register → HAL → C variable. This helped me understand how software data is converted into physical electrical communication between the STM32 and another chip.
